# 계획 30 3회차 (round_03)

날짜: 2026-11-20.

- 차선 예측은 2회차와 같다: `reguide_round.sh round_02 → round_03`, 같은 안내 설정. 차선 검출 코드는 바뀌지 않았다.
- 바뀐 것은 정지선 정답 정의, 정지 위치 대체 기능, 실시간 영상 전달(D1)이다.
- 표: `table.md`, `exclusions.md`. 회차 비교는 `../SUMMARY_KO.md`.

## 1. 정지선 (C4)

정답(`paint_stops`)에서 두 가지를 바로잡았다.

1. **횡단보도 테두리를 정지선에서 뺐다.** 차로 폭을 덮는 가로 막대라도, 0.5 m 안에 줄무늬(차로 폭의 20–75 %, 3 조각 이상)가 0.15 m 넘게 있으면 횡단보도 테두리로 보고 `crosswalk_m` 에 따로 적는다.
   - s1·s8a·s8b 경로 마지막 교차로에는 정지선이 없고 횡단보도만 있다(조감도로 확인).
   - 기준선의 검출 68–70 % 는 이 교차로를 정지선으로 센 탓이었다.
2. **분모를 보이는 부분으로 바꿨다.** 차 바로 앞에서는 BEV 의 보이는 영역이 좁아진다. 그래서 막대 판정을 "보이는 부분이 차로 폭의 절반 이상이고, 그중 80 % 가 칠해짐"으로 바꿨다.
   - 바꾸기 전에는 진짜 정지선이 6–7 m 앞에 올 때 정답에서 먼저 사라져 오검출로 세어졌다(s8b 1.3 %).

결과:

| 장면 | 검출 | 오차 중앙 / p95 cm | 오검출 |
|---|---|---|---|
| s1 | 95.2 % | 3.5 / 9.1 | 0.2 % |
| s7 | 99.5 % | 7.0 / 7.0 | 0 % |
| s8a | 92.4 % | 2.4 / 8.7 | 0.07 % |
| s8b | 93.8 % | 3.0 / 9.5 | 0.4 % |

C4 의 네 기준(검출 ≥ 80 %, 오차 중앙 ≤ 50 cm, p95 ≤ 100 cm, 오검출 ≤ 1 %)을 모두 채운다.

### 정지 위치 대체 (연구 세션 승인)

- `lane_guidance` 의 `stop_line.crosswalk_fallback` 이다. 새 설정이고 코드 기본은 꺼짐이며, launch 에서 `road_markings` 와 함께 켠다.
- 앞에 정지선이 없고 횡단보도가 있으면 그 앞 끝을 `stop_line_m` 으로 쓰고, JSON 에 `stop_source: line | crosswalk` 를 적는다.
- HUD 의 빨간 띠는 `/road/road_markings` 의 `stop_line` 만 그리므로 진짜 정지선일 때만 나온다.
- 시험: `test_traffic_advice.py::test_stop_position_falls_back_to_a_crosswalk_only_when_asked`.
- 지표 `C4_stop_position` 은 정지선, 없으면 횡단보도 테두리를 기준으로 한다. 결과는 s1 73.5, s7 93.1, s8a 72.4, s8b 71.7 % 다.
  - 대체가 별 도움이 안 된다. 검출기가 그 교차로의 횡단보도를 거의 못 찾기 때문이다(`C6_crosswalk` 5–10 %, 참고용, 계획상 C6 는 눈으로 본다).

## 2. 실시간 D1 (연구 세션 결정: 공유 메모리, 3 번까지)

모두 켬(차선 + 노면 표시 + 안내 + 화면 필터 inline + 신호 YOLO 1920 + HUD), town05_30hz 3 번씩. NoMachine 서버와 세션 노드가 켜진 채 쟀다.

| 시도 | 차선 지연 p95 ms | 중앙 ms | 영상 → 수신 p95 | YOLO FPS |
|---|---|---|---|---|
| (2회차) YOLO 가 영상 토픽 구독 | 27.7–28.2 | 23.6–24.2 | 10.2–10.7 | 11.0–11.4 |
| 1. 공유 메모리, 2 프레임에 한 번 | **24.8–25.6** | 21.3–21.6 | 7.5–8.1 | 11.3–11.7 |
| 2. + YOLO 스레드 2, 코어 6·7·14·15 | 24.8–25.6 | 21.2–21.4 | 7.4–7.8 | 11.3–11.4 |
| 3. 3 프레임에 한 번 + 스레드 1, 코어 14·15 | 25.2–26.0 | 21.4–21.5 | 8.0–8.2 | 9.3–9.6 |
| (참고) 신호·표지판 끔 | 23.1–24.1 | 20.7–21.3 | 6.8–7.5 | — |

새로 넣은 것(모두 코드 기본 꺼짐):

- `vision_road/image_share.py`: 블록 구조. 순번을 홀수/짝수로 써서, 쓰는 쪽은 기다리지 않고 읽는 쪽은 덜 써진 영상을 버린다.
- `rt_worker.ros_loop`: 차선 결과와 옆 차로 결과를 보낸 뒤 `image_shm_every` 장마다 블록에 쓴다.
- `node.py` 파라미터 `image_shm_name`, `image_shm_every`. launch 인자는 `image_shm`, `image_shm_every`.
- YOLO 사본 파라미터 `image_shm`(구독 대신 블록을 읽음), `cpu_threads`, `cpu_affinity`.
- `run_lane_hud.sh --signs`: 시도 1 을 기본으로 켠다(`SIGNS_SHM=vision_road_dashcam`).

판정:

- 세 번 다 town05 p95 25 ms 를 확실히 채우지 못했다. 시도 1 이 가장 좋아 그것을 쓴다.
- D1 은 이렇게 닫는다: **이 노트북에서 신호를 켜면 p95 약 25 ms(24.8–25.6), 끄면 23–24 ms. 본체에서 다시 재야 한다.**
- 남은 차이는 차선 처리 p95 +1.5–2 ms(26.1–26.5 vs 24.3–24.9)다. 코어를 묶어도 줄지 않아, 메모리 대역이나 GPU 드라이버 쪽으로 보인다.
- D2(≥ 10 FPS), D3, 빠진 프레임 0 은 시도 1 에서 그대로 충족한다.
- 시도 1 의 영상 수신 → 검출 p95 는 82 ms 다. 공유 메모리에서 읽은 때부터 잰 값이다.

## 3. 닫은 항목 (같은 항목에서 서로 다른 시도 3 번이 실패)

- **B5 / B3:** 아래 세 시도가 실패해 2회차 값(B5 멀 때 60–98 %, B3 74 %)으로 닫는다.
  - `trust_reprojected_line`: s2 에서 목표가 움직임.
  - `match_shifted`(옆 차로를 한 폭 옮겨 목표를 이어 감): s3a 31, s8d 8 번 움직임.
  - `settle_sec` 0.3 / 0.2 / 0: B5 멀 때와 B3(74 → 87 / 91 / 98 %)는 오르지만, 중앙 오표시가 s8b 1.9 → 3.1 / 3.5 / 5.8 % 로 목표를 깬다.
- **A5 오른쪽 재현율(s3a 73, s8c 78 %):**
  - `carla_outer_reach_m` 7.5 는 s3b·s3a·s4 에서 변화가 없었다.
  - 놓치는 경우는 바깥 선이 2–4 m 만 보일 때와 차가 3° 넘게 비스듬할 때다(`round_02` 분석).
  - 1 번만 시도했고, 검출기 바깥 선 단계의 문제라 다음으로 넘긴다.
- **모델 한계(연구 세션 결정, 더 시도하지 않음):** C1 신호 확정(s7 말고 37–49 %), s8b 색 오류 33 %, C3 미국식 SPEED LIMIT·40 표지판.

## 4. s3a 의 정답과 맞지 않는 목표 이동 (81.97 초) 원인

- 81.3 초에 검출된 차로가 한 프레임도 없었다.
- 81.4 초에 차로가 다시 나타났을 때, 이어 오던 목표가 위치로 오른쪽 차로(`right`)에 붙었다.
- 82.0 초의 이동은 그 잘못 붙은 목표가 점선을 넘는 움직임으로 원래 차로로 돌아온 것이다.
- 연구 세션 지시대로 원인만 적고 고치지 않았다(B2 가 나빠질 수 있음).
