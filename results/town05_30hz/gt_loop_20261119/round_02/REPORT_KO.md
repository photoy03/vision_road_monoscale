날짜: 2026-11-20. 1회차 설정에 아래 두 가지를 더해 12 개 장면을 다시 쟀다.

- 측정: `scripts/eval_round.sh round_02 --no-yolo`, `YOLO_FROM=round_00`.
- 지표: `--tag _1920 --sign sign_min_height_px=50 light_max_offcentre=0.3`.
- 표: `table.md`. 회차 비교는 `../SUMMARY_KO.md`.

## 바꾼 것

| 설정 | 어디서 켬 | 내용 |
|---|---|---|
| `carla_centre_heading_m: 8.0` (새 설정, 코드 기본 0 = 지금과 같음) | `carla.yaml` | 차로 중앙선의 기준점 오프셋·방향을 기준점부터 8 m 만의 2 차식으로 구한다(곡률은 그대로 15 m) |
| `guidance.on_m: 0.25`, `guidance.off_m: 0.20` (기존 설정, 코드 기본 0.30 / 0.15) | `maploop.launch.py` | 안내를 0.25 m 부터 보이고 0.20 m 아래로 오면 숨긴다 |

- 방향 설정이 필요했던 이유: 커브가 시작되거나 끝나는 곳에서 15 m 2 차식은 먼 곳의 굽음을 기준점 방향까지 끌어와 미리 꺾었다. s1 13.8–14.3 초가 그렇다(정답 −2.4°, 우리 −5.9°).
- 6·8·10·12 m 를 같은 장면들에 시험했다. p95 기준 8 m 가 가장 좋았다:
  - s1: 1.95 / 1.81 / 1.98 / 2.24°
  - s8b: 2.08 / 2.03 / 2.21 / 2.50°
- 안내 값을 바꾼 이유: 평가가 0.30 m(멀 때)·0.15 m(중앙)를 기준으로 본다. 안내 경계를 그보다 0.05 m 안쪽에 두어, 오프셋 측정 잡음(p95 수 cm)이 표시를 늦추거나 늘리지 않게 했다.
  - 같은 값을 9 개 장면에 걸어 0.25/0.20, 0.27/0.18, 0.25/0.18 을 비교했다. 0.25/0.20 이 모든 장면에서 멀 때 표시는 올리고 중앙 오표시는 낮췄다.
  - 차로 변경 결과는 그대로였다.

### 판정

| 목표 | 결과 |
|---|---|
| D1 차선 지연 p95 ≤ 25 ms (모두 켬) | **미달.** town05 27–28, s7 26.5–26.8, s3a 24.8–25.2. 신호·표지판을 끄면 23.1–24.1 로 충족 |
| D2 YOLO ≥ 10 FPS | 충족: 1920 제한 없음 11.0–11.6 |
| D3 검출 → HUD p95 ≤ 250 ms | 충족: 영상 수신 → 검출 p95 110–114 ms. bridge·안내·HUD 까지의 나머지는 따로 재지 않았는데 수 ms 수준이다 |
| D 빠진 프레임 ≤ 0.5 % | 충족: 0 |

- 신호·표지판을 켜면 차선 지연이 약 3.5–4 ms 늘어난다. 늘어나는 곳은 두 군데다.
  - 영상 → 수신: +3 ms. 같은 6 MB 영상을 받는 노드가 둘이 된다.
  - 차선 처리: +3 ms.
- 이 증가는 YOLO 처리 속도(11 → 5 FPS)나 크기(1920 → 1280)와 거의 상관이 없다. 차이는 1 ms 안이다.
- 그래서 계획의 "10 → 8 → 5 FPS" 단계로는 D1 을 채우지 못한다. 이 단계는 D2 만 깬다.
- 결정:
  - YOLO 는 1920 제한 없음을 유지한다(신호등 확정이 가장 높고 D2·D3 를 채움).
  - `raw_cdr` 는 약 0.5 ms 줄어 `run_lane_hud.sh` 에서 켰다. 검출기 사본의 새 설정으로, 코드 기본은 꺼짐이다.
- D1 을 신호·표지판을 켠 채로 채우려면 영상 전달 쪽을 바꿔야 한다. 연구 세션에 판단을 넘긴다.
  - 공유 메모리 전송
  - 차선 노드가 YOLO 에 영상을 넘기기
  - 본체에서 YOLO 를 다른 장치로 돌리기
