## 한 일

### 1. 필요한 영상 행만 주고받기 (결과 같음)

- 받는 쪽 (`core.Projector`, `rt_worker`, `node`):
  - 잘린 영상을 받으면 BEV 지도를 그 행만큼 옮겨 쓴다(`warp(frame, top)`). 정수만큼 옮기므로 보간이 같고, BEV 가 비트 단위로 같다.
  - 행 위치는 `CameraInfo.roi`(`y_offset`, `height`)에서 읽는다. CameraInfo 토픽은 `camera_info_topic` 파라미터이고, 기본은 영상 토픽 옆의 `camera_info` 다.
  - 읽는 행을 다 담지 않았거나 roi 를 아직 받지 못한 잘린 영상은 버리고 경고를 낸다.
  - 시작할 때 로그에 "the BEV reads image rows 580-981 of 1920x1080" 을 남긴다.
  - 전체 영상과, 폭이 다른 해상도의 영상(예: 1280×720)은 전처럼 처리한다.
  - 오버레이 디버그 영상은 잘린 영상을 전체 크기의 검정 바탕에 넣어 보낸다.
- 보내는 쪽 (모두 기본은 자르지 않음):
  - 재생 도구 `tools/replay_maploop.py --crop-rows 578:984`
  - `tools/realtime_eval.py --crop-rows`
  - `run_lane_hud.sh --crop-rows`
  - 운전 노드 사본 `src/hero_calib` `--ros-crop-rows`
- 약속은 `src/hero_calib/OUTPUT_CONTRACT_KO.md` 의 "대시캠 행 자르기" 에 적었다.
- 보내는 양: 406/1080 행(37.6%), 2.3 MB.
- 확인 (`offline/crop_identity_*.txt`, `scripts/crop_identity.py`): 녹화의 모든 영상에서 전체 영상으로 만든 BEV 와 잘린 영상으로 만든 BEV 가 같다.

### 2. 검출기의 무거운 부분을 C++ 로 (결과도 같음)

- 먼저 쟀다(`metrics/sections_town05.json`, 무거운 10% 프레임 기준). 이진 영상 2.5 ms, 칠 조각 처리 8.6 ms(가닥 합치기 3.0, 사슬 잇기 2.2, 경계석 시험 0.8), 시간 추적 쪽 파이썬 약 6.7 ms(프레임별 선 맞추기 2.5, 이전 선 옮기기 1.0, 통로 거르기 0.5) 등이었다.
- 효과가 큰 것부터, 숫자 계산을 NumPy 와 같은 순서·같은 정밀도로 옮겼다(`vision_road/native.cpp`):

| 옮긴 것 | 내용 | 같게 만든 방법 |
|---|---|---|
| `color_planes`, `ridges` | 이진 영상의 화소별 계산(흰색·노란색 조건, 네 너비의 능선 응답) | NumPy 의 float32 계산 그대로(파이썬 실수 × float32 배열 = float32). `-ffp-contract=off` 로 FMA 를 막음. OpenCV 함수(흐림, 중앙값, 색 변환)는 파이썬에 남김(판이 4.12 와 4.5.4 로 달라서) |
| `edge_like` | 흰 조각마다 경계석 시험을 한 번의 호출로 | NumPy 의 float32 쌍별 합(pairwise sum)을 그대로 구현 |
| `track_match` | 관측한 선과 이전 추적선의 맞춤(12점 중앙값)과 겹친 부분 섞기 | np.linspace, np.interp(C 구현의 경계·NaN 처리), 중앙값 계산 그대로 |
| `corridor_error` | 칠 선이 내 차로 선 통로 안에 있는지 | 위와 같음 |
| `reproject` | 이전 선을 BEV 변환으로 옮기기 | 2항 내적을 이 컴퓨터 OpenBLAS 의 FMA 순서 `fma(b, m1, a*m0)` 로(시험 1만 개 모두 같음) |

- 설정 `carla_native_fast` (코드 기본 꺼짐, `carla.yaml` 에서 켬). 끄면 파이썬 코드가 그대로 돈다. 파이썬 구현은 지우지 않았다.
- **오차 보고**(계획 조정에 따라). Town05 와 maploop 전체 프레임에서 파이썬 결과와 비트 단위로 같다(`offline/native_identity_*.json`). 아래 모든 줄에서 위치 차이는 중앙값·p95·최대 모두 0 m 이고, 5 cm 넘게 다른 프레임 0%, 좌우 선이 바뀌거나 생기고 없어진 프레임 0 이다.

| 영상 | 선 | 프레임 |
|---|---|---|
| Town05 | 내 차로 선(칠 선, 경계) | 1808 |
| Town05 | 바깥 선 | 1808 |
| Town05 | 중앙선 | 1808 |
| maploop | 셋 모두 | 1807 |

- 남은 위험: `reproject` 는 이 컴퓨터의 OpenBLAS 가 쓰는 FMA 순서를 따랐다. BLAS 커널이 다른 CPU(예: AVX-512)에서는 NumPy 쪽이 마지막 비트에서 달라질 수 있다. C++ 결과는 어느 컴퓨터에서나 같다. 시험은 1e-12 이내로 확인한다.

### 3. 표시 필터 (결과 같음)

- 표시선 메시지를 만들 때 `Point(x=, y=, z=)` 대신 필드 검사 없는 생성을 쓴다(점 35개에 46 µs → 5 µs). 직렬화된 바이트가 같다는 것을 확인했다.
- import 를 한 번만 하게 했다.
- 보인 끝의 중앙값(3개 이하)은 np.median 대신 정렬로 구한다(같은 값).
- 맞춤의 np.interp 는 래퍼 없이 부른다.
- 확인: 메시지가 Town05 1808/1808 프레임 같다(`offline/display_identity_town05.txt`). maploop 에서는 재지 않았다(같은 코드 경로).
- 평균 0.27 ms 줄었다. 나머지(이차 맞춤의 선형대수, 1-euro 필터)는 결과를 바꾸지 않고는 더 줄이기 어려웠다.

### 4. AI 필터를 켰을 때도 빠른 경로 (기준 설정에 영향 없음)

- 지금까지는 가중치를 주면 영상이 road_node 를 거쳐 계산 프로세스로 갔다(구조 차이 +4.4 ms).
- 이제는 road_node 가 모델 프로세스를 만들고, 그 파이프와 공유 메모리를 계산 프로세스에 넘긴다(`LaneMaskProcess.handle()` → `LaneMaskClient`).
- 계산 프로세스가 카메라를 직접 받아 모델에 영상을 넣는다. 순서는 전과 같다(가장 새 마스크를 받은 뒤 이 프레임을 넣음).
- 설정 `learned_in_worker` (코드 기본 꺼짐, `carla.yaml` 에서 켬). 가중치가 없으면 아무것도 바뀌지 않는다.
- 잘린 영상과 같이 쓰면 모델은 행 밖이 검정인 영상을 본다. 그 마스크가 전체 영상의 마스크와 얼마나 다른지는 재지 않았다. 그래서 AI 필터의 공식 수치는 전체 영상으로 쟀다.
- AI 필터 켬의 단계(전체 영상, 평균/p95 ms): 영상 받기 6.1 / 6.9, 검출 12.2 / 15.8(모델 프로세스와 CPU 를 나눔), 표시 2.8 / 3.6, 모델에 넘기기 0.3 / 0.7.
- 이전 AI 필터 측정(41–44 ms, 계획 18)에는 안내와 가짜 차량 상태가 없었다. 이번 측정에는 둘 다 켜 있다.

## 25 ms 에 대해

- **기준 설정은 잘라 보내기로 채웠다**(23.4–24.2 ms).
- 남은 시간(p95 대략): 영상 받기 4.3, BEV 0.8, 검출 14.2, 표시 3.5, 그 밖 1 ms.
  - 검출 14.2 ms 의 큰 몫: 이진 영상의 OpenCV 단계 약 2.3, 가닥 합치기(쌍 투표 포함) 약 3.0, 사슬 잇기 약 2.2, 시간 추적의 나머지 파이썬 약 3 ms.
  - 이 부분을 C++ 로 옮기면 더 줄 것으로 보지만, 옮기는 양이 많고 결과를 비트 단위로 같게 만들기 어렵다(정렬 동점, 반복 맞춤).
- **전체 영상은 25.9–26.9 ms** 다. 영상 받기가 약 6 ms 로 2.3 ms 더 든다. 운전 노드도 `--ros-crop-rows 578:984` 로 보내면 기준 설정과 같아진다.
- **AI 필터는 27.9–28.8 ms**(전체 영상)다. 이 노트북에서는 모델 프로세스가 CPU·메모리를 같이 써 검출이 1.2 ms 느려진다. 잘라 보내기와 같이 쓰면 26.3 ms 다.
- 더 빠른 CPU 에서의 어림(재지 않음):
  - 차선 쪽은 코어 하나의 속도가 정한다. 단일 코어가 30% 빠른 CPU(요즘 데스크톱 CPU 는 5800H 보다 대략 그만큼 빠르다)라면 검출·표시·영상 받기가 대략 그만큼 줄어든다.
  - 그러면 기준 설정 p95 는 18–20 ms, AI 필터 켬도 25 ms 안쪽일 가능성이 크다.
  - GPU(5070)는 모델을 빠르게 하지만, 모델은 따로 돌아 표시선 지연에는 직접 들어가지 않는다.
  - CPU 이름을 알면 더 좁힐 수 있다. 가장 좋은 것은 그 컴퓨터에서 `tools/measure_latency.sh` 를 돌리는 것이다.
- CPU 코어 묶기는 하지 않았다(이전에 효과가 없었다).

## 확인하지 못한 것

- 5070 컴퓨터에서의 실제 수치.
- 잘린 영상으로 AI 필터 모델을 돌릴 때 마스크가 달라지는 정도.
- 운전 노드 사본의 잘라 보내기를 실제 CARLA 에서 돌린 것. 함수와 메시지는 시험으로만 확인했다.
- 실시간 실행끼리의 출력 비교. 실시간은 같은 코드로도 실행마다 출력이 조금씩 다르다(이전 코드 두 번 실행의 경계선이 1578/1808 프레임만 같음). 차량 위치 메시지가 도착하는 시점이 다르기 때문으로 보인다. 그래서 출력이 같다는 것은 오프라인 비교로 확인했다.
- 실시간 지표: 표시선이 차 근처부터 그려진 비율이 이번 실행 0.91–0.95 로, 계획 24 의 0.75–0.87 보다 높았다. 처리가 빨라진 영향으로 보이지만 원인은 따로 확인하지 않았다.
